## Acceptance criterion

The intended boundary is a detailed mathematical/Lean skeleton **assuming the
correctness of explicitly stated analytic theorems**. Reproving all that
analysis in Lean is not a condition of this specification milestone. The
analytic assumptions must nevertheless be the exact theorems needed, rather
than superficially similar assertions with different domains, thresholds or
strictness.

The implementation handoff is adequate only when a developer can identify,
without inventing another mathematical argument:

1. The semantic meaning and units of every input and output.
2. Every applicability gate, including positive denominators, index ranges,
   signed moments and degenerate cases.
3. The exact conclusion certified over an entire continuous cell.
4. All original domains, required branches, seams and infinite tails.
5. Which analytic results are trusted assumptions and which numerical facts
   the certificate checker must establish.
6. The exact assembly rule consuming those facts.

Compilation alone does not meet this criterion. Conversely, a clearly stated
source-exact analytic theorem parameter is not an implementation ambiguity
merely because its full proof remains external at this stage.

## Finding A01: ROOT4 is a weak bound, not an equality exclusion

**Severity: P1. Initial finding confirmed against both theorem and checker.**

The source theorem `n4all:thm:main`, line5490, concludes
`C_4 <= T`, where `T=4097/10000`. Its proof ends with the explicit statement
that the equality case `C_4=T` is not excluded (around line6174). The actual
checker `be_replay/root4.py`, line398 at the baseline, accepts
`not pending and upper <= TARGET`.

The first generalized draft instead required `StrictScoreBound w`, namely
`score(w) <= T - margin` for a positive rational margin, for **every**
`ContactAt 4 T`. This is a stronger assertion than the source: it rules out
an attained equality contact and is not supplied by a weak numerical bound.

Required resolution: retain a strict contrary hypothesis `T<C_4`, extract
the appropriate unrestricted maximizing witness, then consume a **weak**
`ScoreCap w (4097/10000)`. The equality `w.optimal` relates this bound to
`C_4`, yielding the contradiction. No positive gap below T is required.
Localization must concern the chosen owner under the strict violation;
it must not assert quantitative localization for every unrelated contact
without the source's assumptions.

Acceptance check: a certificate whose complete upper bound equals T must
typecheck as valid evidence for `C_4<=T`. It must not be rejected for lacking
a positive rational margin. The separate `StrictScoreBound` type is useful
for genuinely strict methods but is not the ROOT4 contract.

## Finding A02: a regional COUNT proof cannot require global COUNT

**Severity: P1. Quantifier mismatch in the first typed pipeline draft.**

The initial `MethodEvidence.supportedCount` constructor for one contact w
required a `ContactPipeline n floor` whose stages quantified over **all**
`ContactAt n floor`. The source supplies regional COUNT/resource proofs;
the n5 gap-free corner and Fourier complement are separate methods. Requiring
the selected COUNT method for one contact to prepare every contact would
silently demand central gaps and COUNT evidence outside its source domain.

Required resolution: pointwise supported-count evidence indexed by this w,
or a pipeline with an explicit eligibility domain threaded through every
stage. Universal quantification belongs in the outer region-provider theorem.
A convenience globally quantified pipeline may remain, but it cannot be
mandatory for a regional evidence constructor.

Acceptance check: ordinary low-rho COUNT evidence for n5 can be supplied
without also providing a central-gap acquisition for the support-free corner.

## Finding A03: raw and normalized CDFs require an explicit bridge

**Original severity: P1. Resolved in the mandatory normalization interface.**

`ContactAt.positive_closed` is expressed at the normalized threshold z.
The contact polynomial, physical remainder and count mixture use the raw
threshold `H=sqrt(n)z`. These CDF expressions are mathematically equivalent
for positive n, but not definitionally identical Lean expressions.

The exact required assertion is

```
n > 0,
rawCDF(w) - Phi(w.threshold.value) = Delta_n(w.X).
```

`ContactNormalizationEvidence` makes this a named analytic normalization
contract, and count-to-score normalization must consume it. An implementation
must not choose its own scale conversion or treat a raw H as normalized z.

## Finding A05: ROOT4 has a third, different defect and reference law

**Severity: P1 for a numerical implementation contract.**

`n4all:eq:reference`, line5518, defines the canonical three-point reference
Q3 using the actual signed beta and positive first moment u:

```
a=(1-beta)/(2u), b=(1+beta)/(2u), w=4u²/(1-beta²),
Q3=(u/a)delta(-a)+(1-w)delta(0)+(u/b)delta(b),
eta=rho(P)-rho(Q3).
```

This eta differs both from the matching-two-point defect and from the physical

actual law P to three atoms. The same actual weighted measure is used for all
priced frequency responses.

Required resolution: a distinct ROOT4 state and source-exact bounded-owner
scope. The target theorem alone is a legitimate abstract analytic premise,
but it is not enough information to implement the physical ROOT4 checker.

## Finding A07: semantic witnesses are not runtime job inputs

**Severity: P1/P2 depending on the final certificate contracts.**

Functions quantified over an unknown extremal probability law w are semantic
proof interfaces. A numerical executor cannot serialize or inspect this
unknown law. It receives a fixed rational task context, and the theorem
interpreting its certificate quantifies over all actual laws satisfying that
context.

Required resolution: at least one fully specified concrete COUNT task context
and certificate meaning. It must bind n, target, original domains, support and
resource assumptions, count/phase conventions and source family. The soundness
statement should have the form

```
accepted(context,payload)
    -> for every actual law/contact satisfying the fixed context,
       the complete original-root/leaf conclusion holds.
```

The generic `CertificateChecker Payload Meaning` correctly exposes the trust
boundary, but its caller must not be left to invent the actual Meaning or
decide which context fields are part of the assumptions.

### A08: the fifth COUNT coordinate is a0, not total inward displacement

**Severity: P1. A concrete variable-meaning mismatch in the typed draft.**

The selected numerical roots are `(p,lambda,alpha,u,a0)`, as documented by
the actual engine readback in `proof/code_count_engine_audit.md`, line63,
and `proof/code_count_kernel_audit.md`, line356. The physical conditional
supports are `U0 in[-O0,a0]` and `U1 in[-a1,O1]`.

The first typed realization equated this fifth coordinate with
`CentralGap.inward`, which is the **sum** dY=a0+a1. For the actual central
gap(-A,B), the correct individual coordinates are

```
a0 = p-h*A,
a1 = (1-p)-h*B,
dY = a0+a1 = 1-h*(A+B),       h=pq/m.
```

The cap d0 bounds the sum; it also bounds a0 because a1>=0, but that does not
make these coordinates equal. A certificate leaf split on a0 must be
interpreted at actual a0, not at the total dY.

Required resolution: use an unambiguous raw-a0 name in `CountPoint`, bind
the realization to its individual endpoint formula, and retain dY separately
in the resource/joint budget. This also fixes the corresponding frozen
context field semantics.
