# Fresh ordinary COUNT execution

This implementation adds a second explicitly typed project to the same CLI:

```console
be run examples/count-native/project.toml --resume
```

On Windows, use a short `--state-dir` if the checkout path is long. Runtime
profile `be.native-python-runtime/2` requires unoptimized CPython 3.12 and the exact public dependency
lock used by the coordinator. The native mathematical child uses only the
standard library with `-E -B -S`; it does not import coordinator packages.

The supported statement is precisely the complete ordinary forest
`n6.B0.p61`, with the literal positive-class interval `[61/100,31/50]`.
It contains all seven original count roots. The exact score, target,
conditional resource hypotheses, five axes, phase interval and right-half
interpretation are recorded by the [source adapter](COUNT-NATIVE-PLAN.md).
This result is `SCOPED_COUNT_PASS`. Parent same-law resources, all-law C6,
all-index bounds and the final theorem remain separate obligations.

## Fresh execution and resume

1. Verify the exact 29-file source capsule. The capsule contains neither a
   historical candidate forest nor a historical acceptance receipt.
2. Freeze the mathematical statement, source epoch, complete native runtime,
   coordinator code/dependencies, limits and local authority identity into an
   immutable campaign. Resume cannot reset its absolute deadline.
3. In a new private directory, construct a complete forest from these sources.
   Store the whole candidate as untrusted immutable bytes.
4. In another new directory and process, replay the complete native acceptor.
   Reconstruct every original leaf and both sides of every closed split,
   reevaluate the numerical inequalities and execute all 24 native controls.
   Validate the exact native receipt and its forest/source/kernel bindings.
5. After unchanged source/runtime readback and successful process cleanup,
   authenticate the exact stage payload with the private local coordinator key
   and commit it through the current ledger lease generation.
6. On resume, verify the authentication, every referenced artifact, exact
   campaign/source/runtime/whole-candidate key and complete structural census.
   An authenticated completed expensive checker need not run again.

Native JSON and diagnostic timings are opaque byte artifacts. They are not
silently converted into the restricted, number-free mathematical RJSON
format. Their authenticated wrapper uses explicit string counters and exact
rational texts. Paths and timings do not establish a numerical inequality.

The immutable CAS checks complete SHA256/length/type on reuse. SQLite claims,
heartbeats, retry generations and fenced completion prevent a stale attempt
from publishing over a current attempt. The heartbeat covers parent-side
environment checks as well as native execution. A failed or interrupted stage
does not yield PASS; already committed stages remain resumable.

## Trust and resource boundary

The private `authority.key` is operational state outside the certificate CAS.
Its HMAC authenticates that this local trusted coordinator observed this
specific checker execution. It is neither a portable mathematical certificate
nor a Lean proof. An independent replicator constructs and checks the forest
again. An unsigned success word in a ledger or a worker file cannot authorize
cache acceptance. Losing or changing the key invalidates old cached authority.
Host administrators and same-user code able to read this key are inside the
local trust boundary; this is not a hostile-host execution design.

Windows uses a private Job Object assigned before the child's first resume,
with aggregate CPU/memory and kill-on-close process-tree cleanup. Linux uses
an exec guard, per-process CPU/address-space limits and private process-group
cleanup, including a parent-death guardian. The Linux profile does not claim
aggregate cgroup/RSS enforcement or protection from hostile process-group
escape. Only the pinned reviewed sources may run under this profile.
Both profiles enforce wall/deadline and bounded retained logs. The runner
requires successful completion, exit zero and confirmed tree cleanup.
The runtime inventory binds ordinary file bytes and each bounded literal file
link chain together with its resolved target bytes. Broken/cyclic links and
directory aliases are rejected. Source/runtime pre/post scans are separate;
directory checks are memoized only inside a single scan.

This one-forest dependency is sequential: construction precedes acceptance.
The bulk portfolio can run independent frozen-context forests in parallel;
final proof composition still waits for fresh exact same-law resource
licenses. The bounded-batch runtime guard must finish before provisional
batch outputs become accepted. See [concurrency review](CONCURRENCY-REVIEW.md)
and the [whole-proof gap ledger](END-TO-END-GAP-LEDGER.md).
