## Fresh output and execution evidence

Each action gets a fresh sealed private capsule containing its complete selected
input/source closure. Its own historical accepted output is excluded. The child
executes the exact original source using `python -B -S`, original arguments and
the selected working directory. No new search, evaluator shortcut or saved
probability oracle is introduced.

The entire newly written receipt is requested as a stopped-supervisor output
capture. Validation requires the native file, copied capture, original source
path, captured path, byte count and SHA-256 to agree. A historical PASS word,
standalone receipt or partial checkpoint cannot complete a stage. Where the
original prints the full receipt as JSON, that actual terminal packet must equal
the whole fresh file. A text-only strict checker must emit its exact source-bound
terminal prefix, argument count and literal probability index.
Its passing/excluded/all-leaf/control counts and floating display of the exact
maximum must also match the whole fresh receipt; elapsed metadata must be finite
and nonnegative. These terminal fields follow the common literal print expression
checked in all 51 selected strict entry-source variants.

The observed ledger initially has false completion/acceptance flags. Readback
checks the real launch and stopped supervisor result, exact command/cwd/output
context, complete capture request, source closure, current runtime hashes,
literal budgets, exact integer return code zero, actual stdout/stderr hashes,
empty stderr and finite process diagnostics. It also recounts the candidate
topology without evaluating a leaf and compares the source-selected full census.

Only after all these checks is a complete ledger written and revalidated.
`finite1039_count_evidence.validate_completed(task)` can revalidate a relocated
stage using its single explicit original task prefix. Original receipts,
captures, commands and launch bytes are never rewritten. This validator imports
only new metadata/infrastructure helpers; it does not rerun mathematical code.

## Resource scope, progress and cache

Each action has the explicit BASIC policy: 2 GiB memory policy,
43,200-second per-process CPU and 54,000-second external wall ceiling, a
512 MiB sampled private-disk ceiling and 16 MiB log ceiling. Per-process hard
AS/CPU limits and sampled live process-group CPU/RSS are distinguished from
cumulative CPU of reaped descendants, aggregate kernel memory enforcement,
cgroup/Windows-Job equivalence and containment of descendants changing sessions.
The latter guarantees are not claimed. These are action budgets, not a batch
runtime estimate.

Actual stdout and heartbeat diagnostics appear every 20 seconds. Minute backups
contain logs and ledgers, not an accepted numerical prefix. A completed stage is
fully revalidated before export as ZIP plus SHA-256 sidecar. Cache import checks
the sidecar and bounded canonical member inventory before extraction, rejecting
traversal, links, encrypted members, duplicate/case-colliding paths and incomplete
evidence. A relocated restore must pass the complete current source, execution,
receipt and ledger validation before numerical replay may be skipped.

Interrupted arithmetic is rerun fully. Corrupt, incomplete, incompatible or
wrong-job cached stages are advisory and rejected. Complete earlier stages
remain reusable if a later action fails. A final result bundle is saved on
success or handled failure. Only archive assets needed by the selected lane are
obtained, with full original size/SHA checks before source extraction.
