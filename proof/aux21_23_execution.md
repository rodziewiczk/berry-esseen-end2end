# Conditional auxiliary21--23 replay protocol

This is a new execution and same-object edge protocol around unchanged
archived numerical entry points. Preparation, source hashing, JSON census
checks and synthetic/mocked fixtures have been performed locally. No
INITIAL engine, resource contraction, count evaluator or optimization
comparison was imported or executed locally. Their fresh execution is
reserved for Colab.

The jobs can run in parallel. A job's predecessor is an explicit
conditional mathematical statement, not a historical accepted receipt.
Only a later reviewed acquisition join can discharge that statement and
the retained analytic implications. These jobs never issue a full
auxiliary bound, stronger24 acquisition or all-index conclusion.

## Explicit resource-to-count edges

   `initialNN_proof.json` have identical bytes; the fresh resource receipt

## Native and BASIC execution contracts

The selected transitive imports of the INITIAL, resource and count
acceptors consist of local frozen pure Python and the standard library.
Their inspected call paths do not start threads/processes or use ctypes,
Windows APIs or `resource` limits. They use the existing reviewed
`trusted_native` single-process seccomp supervisor, requiring64 MiB
controller plus448 MiB worker address-space caps. Default per-action hard
CPU is7,200 seconds (30 controller and7,170 worker), with7,260 seconds
outer wall time. A failed/unavailable native capability never falls back
to discovery mode for these acceptors.

The n23 `check_optimization.py` is deliberately different: its unchanged
main launches a separate unmodified slow parent-directory process. Both
the slow parent closure and its five selected candidate objects are
included. This single corroboration stage runs under the explicit BASIC
POSIX process-group supervisor and reports `native_arithmetic_accepted:
false`. It must freshly compare70 complete exact cell dictionaries and
1,000 deterministic rational quartics. No old
`OPTIMIZATION_EQUIVALENCE.json` is imported. These finite comparisons
corroborate the exact optimization identities; the stated identities
remain a source/analytic review obligation.

Stages22 and23 comprise12 and25 separate bounded actions, respectively;
stage21 has one. These are per-action ceilings, not runtime estimates or a
promise that the whole job finishes within a single action's budget.
Completed stages are reused only after their full evidence validation.

Every accepted stage requires exact integer return code zero, current
source and supervisor hashes, the actual required guard, empty stderr,
and actual stdout/stderr hashes matching both supervisor and stage
captures. Exact original terminal objects/markers, source/candidate
bindings, controls and complete censuses are checked. The sealed selected
source tree is verified before and after; only explicitly named fresh
outputs are permitted. Interrupted outputs without a successful guard
record are preserved separately and never treated as completed evidence.

The targets are strings `'21'`, `'22'` and `'23'`. The return object has
`status`, `bundle` and `work`. Defaults are
`work_root='/content/berry-esseen-runs'`,
`archives='/content/berry-esseen-archives'`, `backup_interval=60`,
`wall_seconds=7260`, `cpu_seconds=7200` and `resume=True`.

Actual new worker output is relayed alongside a20-second heartbeat.
The supervisor records its own resource/progress observations. Live
evidence is copied every60 seconds to the chosen durable directory.
On a handled error or completion, the status and final evidence ZIP with
SHA-256 sidecar are preserved. These jobs do not resume partial numerical
cells. Matching live evidence may restore a complete stage ledger; every
such stage must pass source, guard, capture, candidate and receipt checks
before reuse. A new incomplete stage is rerun in a fresh execution epoch.

The public read-only export verifier is:

