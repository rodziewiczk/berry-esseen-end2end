## Candidate replay and fresh input edges

The supplied INITIAL, resource and local proof JSON objects are candidate data for the full acceptors. The driver does not repeat construction merely to regenerate the same numeric object. Their complete numerical contents must match the unchanged acceptor's fresh recomputation.

For B0–B2, the accepted INITIAL proof is copied under the resource protocol's fixed lowercase input filename in both resource implementations. The resource receipt binds that exact newly accepted parent. B2's local protocol also retains two literal parent-receipt pins. The original INITIAL and fixed-point resource receipts contain no timing/interpreter fields, so the source route is intended to reproduce their exact deterministic bytes. The driver preserves the original checks and fails if they do not match; it never inserts archived acceptance receipts to satisfy them.

B3–B5 resource acceptance receipts contain elapsed seconds. The original local candidate's `parent_binding_sha256` therefore needs the hash of the actual fresh resource acceptance. The driver creates an explicitly recorded **untrusted candidate derivation** that changes only that one metadata hash. It rejects any other changed parent hash and verifies that every numerical proof field is unchanged. It then runs the original full local acceptor, which recomputes the complete covers/resource cycles and requires full-object equality. `*-CANDIDATE.json` records the original/derived candidate hashes and the precise changed binding. No numerical Python source or old guard is changed or monkeypatched by this driver.

## Execution and progress

The unchanged local drivers and fixed-point comparisons launch subprocesses. They run under the existing BASIC POSIX process-group supervisor. It applies per-process address-space/CPU limits and samples group CPU/RSS, disk and logs; it is not the stronger single-process seccomp/cgroup contract. Accordingly `native_arithmetic_accepted`, `branch_theorem_acquired`, `stronger24_acquisition_verified` and `all_index_conclusion_verified` remain false even after complete arithmetic.

Defaults are 7,200 CPU seconds and 7,260 wall seconds **per native action**, with a sampled 512 MiB process-group memory ceiling. These ceilings are configurable through the Python API; no measured suitability or completion time is claimed before Colab execution. A bounded stop is partial evidence and cannot produce a complete branch result.

Actual native output and supervisor CPU/RSS progress are displayed every 20 seconds. A Drive backup runs every 60 seconds. Each session uses a fresh `stronger24-bN/<timestamp>` directory and saves a final ZIP and SHA sidecar, including failure captures, when Python can execute its finalizer. A disconnected or destroyed runtime can only leave the last completed Drive backup.

There is **no automatic resume or accepted-stage reuse** in this first driver. A new RunAll starts a new execution epoch and preserves previous evidence. An interrupted native action has no internal restart checkpoint. Completed stage reports in a partial bundle remain available for inspection, but this driver does not silently splice them into another run.

Only the known invalid-escape-sequence `SyntaxWarning` is filtered during child launch. Prior warning policy is restored afterward. Other warnings/errors must still leave an empty stderr capture for a stage to complete. Stdout and stderr must be ordinary bounded files whose SHA-256 values match the actual supervisor receipt, including the empty stderr hash.
